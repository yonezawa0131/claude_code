# slide-html-generator

`slide-deck-builder` が出力した設計書 `SLIDE-DECK-{name}.md` を入力として、実際に表示できる完成HTMLスライドを1枚ずつ生成する。設計書には「Deck Info・Design System・Slide Patterns・Slides」の全情報が自己完結で含まれているため、外部ファイルを追加で参照しなくてもスライドを組み立てられる。

このスキルの中核は**サブエージェントによる並列生成**である。スライド枚数が多くても、複数のサブエージェントが同時にHTMLを書くため高速で、かつ後述のトークン効率設計により大規模なデッキでも破綻しない。

## 役割分担（このスキルの設計思想）

- **司令塔（メインエージェント）**：設計書の解析、バッチ分割、サブエージェントの起動、検品、ビューア生成を担当する。**自分ではスライドHTMLを1枚も書かない。**
- **手足（サブエージェント）**：割り当てられた2〜4枚のスライドHTMLだけを書く。Design Systemと担当パターン以外の情報は知らない。

**なぜこの分担にするか（トークン効率上の理由）：**

1. **司令塔のコンテキストを肥大化させない。** スライドHTMLは1枚あたり数百行に及ぶことがあり、全スライドを司令塔が直接書くと、生成済みHTMLがすべて司令塔のコンテキストに積み上がり、後半になるほど遅く・不安定になる。司令塔は「どのスライドを誰に任せたか」だけを保持し、HTML本文は各サブエージェントのコンテキスト内で完結させる。
2. **サブエージェントには必要最小限のみ渡す。** 各サブエージェントが担当するのは数枚だけなので、そのスライドが使うパターン定義とコンテンツ仕様さえあればよい。SLIDE-DECK.md全文（他バッチのスライド仕様や未使用パターン）を渡すのは無駄なので渡さない。
3. **並列化で総時間を短縮する。** 各バッチは互いに独立しているため同時実行できる。

## 起動条件

- 「スライドを生成して」「SLIDE-DECKからHTMLを作って」「スライドを完成させて」などと言われたとき
- `slide-deck-builder` で SLIDE-DECK.md を生成した直後に、続けてHTML化を求められたとき

## STEP 1：入力の特定

カレントディレクトリで設計書を検索する：

    SLIDE-DECK/SLIDE-DECK-*/SLIDE-DECK-*.md

### 1件だけ見つかった場合

> 「設計書 `SLIDE-DECK/SLIDE-DECK-{name}/SLIDE-DECK-{name}.md` が見つかりました。これをHTMLスライドに変換します。よろしいですか？」

承認を得たらSTEP 2へ進む。

### 複数件見つかった場合

各ファイルの Deck Info（title）を読み取り、番号付きで提示して選んでもらう：

> 「以下の設計書が見つかりました。どれをHTML化しますか？番号で教えてください。
>
> 1. `SLIDE-DECK/SLIDE-DECK-{name1}` — [title1]（[N1]枚）
> 2. `SLIDE-DECK/SLIDE-DECK-{name2}` — [title2]（[N2]枚）
> ...」

選ばれたファイルをSTEP 2で解析する。

### 1件も見つからない場合

> 「設計書（SLIDE-DECK.md）が `SLIDE-DECK/` フォルダに見つかりませんでした。`slide-deck-builder` スキルでSLIDE-DECK.mdを先に生成してから、このスキルを再度呼び出してください。」

→ スキルを終了する。

## STEP 2：設計書の解析（司令塔の仕事）

選択した SLIDE-DECK.md を司令塔が読み込み、以下を把握する。**ここで得るのは「構造と行範囲」であって、本文を丸ごとコンテキストに保持し続ける必要はない**（本文はサブエージェントがファイルから直接読む）。

1. **Deck Info** — `title` / `audience` / `purpose` / `slide_count`。出力フォルダ名 `{name}` もファイルパスから確定する。
2. **Design System セクション** — このセクションが SLIDE-DECK.md の**何行目から何行目まで**かを記録する（`## Design System` 見出しから次の `## Slide Patterns` の直前まで）。全スライドが従う共通定義なので、全サブエージェントに渡す。あわせて Primary色・ベースフォント・スライドサイズ等の**主要デザイントークンだけ**は司令塔のメモとして控えておく（STEP 4の検品で使う）。
3. **Slide Patterns セクション** — 使用パターン名の一覧と、各 `### Pattern: {name}` 定義の**行範囲**を記録する（パターン名 → 開始行・終了行の対応表を作る）。
4. **Slides セクション** — 各スライドについて `number` / `type` / `pattern` と、その `### Slide N` ブロックの**行範囲**を記録する。

司令塔が最終的に手元に持つのは「行範囲の対応表」であり、HTMLでもパターン本文でもない。これが司令塔のコンテキストを軽く保つ鍵である。

## STEP 3：バッチ分割と並列生成

### バッチ分割

Slides を**2〜4枚ずつのバッチ**に分割する。目安：

- 標準的なスライド（箇条書き・カード・見出し）が中心 → 4枚/バッチ
- チャート・複雑なSVG図解・大きなテーブルを含む → 2枚/バッチ
- 1つのバッチには**同じパターンや近いパターンのスライドをまとめる**と、サブエージェントが読むパターン定義が減って効率的（必須ではない）

分割したら、各バッチにつき Agent ツールでサブエージェントを1つ起動する。**バッチが複数ある場合は並列で起動する**（依存関係が無いため、同一ターンでまとめて起動してよい）。

### モデルの選択

- 既定は `model: "sonnet"` を**明示的に指定**する。スライドHTMLの生成は定型的で、Sonnetで十分な品質・速度・コストが得られる。
- 例外的に `model: "opus"` へ昇格してよいのは、そのバッチに**複雑なデータチャート（多系列グラフ・込み入ったSVGダイアグラム・緻密なインフォグラフィック）**を含むスライドがある場合のみ。判断基準：「Elementsに chart / diagram / infographic 系の要素があり、座標計算やSVGパス構築を要する」ならOpus、それ以外はSonnet。昇格は該当バッチだけに限定し、単純なスライドまでOpusにしない（トークン効率のため）。

### 各サブエージェントへ渡す情報（トークン効率の中核ルール）

**採用方式：ファイルパス＋行範囲 Read 方式。** 司令塔はプロンプトに設計書本文を転写せず、**「SLIDE-DECK.md の絶対パス」と「読むべき行範囲」だけ**を伝え、サブエージェントに自分で Read させる。プロンプトへの本文転写より司令塔・サブエージェント双方のトークンを節約でき、コピペによる欠落・改変も避けられる。

各サブエージェントへ渡すプロンプトには次を含める：

1. **設計書の絶対パス**（例：`/…/SLIDE-DECK/SLIDE-DECK-{name}/SLIDE-DECK-{name}.md`）
2. **Design System セクションの行範囲**（STEP 2で記録）。「この範囲を Read して、色・タイポグラフィ・Slide Frame・余白などデザイン定義に必ず従うこと」
3. **担当スライドが使うパターン定義の行範囲のみ**（担当バッチで使うパターンだけ。他パターンの範囲は渡さない）
4. **担当スライドの仕様ブロックの行範囲**（担当する `### Slide N` の範囲だけ。他バッチのスライドは渡さない）
5. **出力先の絶対パス**（後述の命名規則で、担当スライドそれぞれのファイルパスを明示）
6. **スケルトンHTMLの参照先**（後述）

**渡してはいけないもの：** SLIDE-DECK.md 全文、他バッチのスライド仕様、担当外のパターン定義、既に生成済みの他スライドのHTML。サブエージェントは自分の担当範囲だけを見る。

**サブエージェントへ渡すプロンプトの例**（Slide 5・6 を担当、両方 `four-card-2x2` を使うバッチの場合）：

> 「あなたはHTMLスライドを生成する担当です。設計書 `/…/SLIDE-DECK/SLIDE-DECK-{name}/SLIDE-DECK-{name}.md` から、指定した行範囲だけを Read して作業してください。他の行や他ファイルは読まないでください。
>
> - Design System（全スライド共通のデザイン定義）：この設計書の **12〜98行目**。色・タイポグラフィ・Slide Frame・余白を必ずこの定義に従わせること。
> - パターン定義 `four-card-2x2`：**140〜175行目**。レイアウト構造の指定。
> - 担当スライドの仕様：Slide 5 は **210〜225行目**、Slide 6 は **226〜240行目**。ここに書かれたコンテンツを実テキストとして流し込むこと。
> - 構造の参考スケルトン：`/…/docs/SLIDE-PATTERN/SLIDE-PATTERN-four-card-2x2/SLIDE-PATTERN-four-card-2x2.html` を Read し、外枠（scale(0.75) 表示規約）とグリッド構造を土台にする。ただしグレーのダミー色はDesign Systemの実際の色に置き換えること。
> - 出力：Slide 5 を `/…/slides/slide-05.html`、Slide 6 を `/…/slides/slide-06.html` に、それぞれ自己完結HTML（外部依存なし・インラインCSS・1920×1080固定）として Write すること。
>
> 完了したら生成した2ファイルのパスだけを報告してください。」

司令塔は上記のように**行番号を埋めた具体的なプロンプト**を各バッチ分だけ用意し、同一ターンでまとめて Agent ツールを起動する。

### スケルトンHTMLの参照

各パターンには構造の見本となるスケルトンHTMLがある。サブエージェントには、担当パターンのスケルトンHTMLを構造の**参考**として読み込ませる（そのままコピーするのではなく、Design Systemの色・フォントを適用し、コンテンツ仕様の実テキストを流し込む土台にする）。参照先は次の順で解決する：

- カレントディレクトリに `SLIDE-PATTERN/SLIDE-PATTERN-{name}/SLIDE-PATTERN-{name}.html` があればそれ
- 無ければ、このSKILL.mdのあるフォルダから見た `../../docs/SLIDE-PATTERN/SLIDE-PATTERN-{name}/SLIDE-PATTERN-{name}.html`（プラグイン同梱パターン）

どちらの絶対パスを使うかは司令塔がSTEP 2の時点で確認し、サブエージェントには**解決済みの絶対パス**を渡す。

### 各スライドHTMLの要件（サブエージェントへの指示に含める）

- **完全に自己完結**：外部CSS・外部JS・外部フォント・外部画像を読み込まない。CSSはすべて `<style>` にインライン、画像が必要な箇所はプレースホルダー（塗り＋ラベル）かインラインSVGで表現する。
- **サイズは1920×1080固定**。スケルトンHTMLと同じく `transform: scale(0.75)` で表示する表示規約に準拠する（`.slide-outer` 幅1440px、`.slide-wrapper` に `transform: scale(0.75); transform-origin: top left; margin-bottom: -270px`、`.slide` は1920×1080）。この外枠構造はスケルトンHTMLをそのまま踏襲すればよい。
- **Slide Frame の踏襲**：タイトルエリア・ブランドフッター・ページ番号など、Design Systemの `Slide Frame` で定義される共通枠を各スライドに反映する。ページ番号にはスライド番号を入れる。
- **デザイントークンの厳守**：背景・Primary色・アクセント色・見出し/本文のフォントサイズは Design System の定義値を使う。スケルトンHTMLのグレーのダミー色（`#E8E8E8` 等）はDesign Systemの実際の色に置き換える。
- 文言は担当スライドのコンテンツ仕様（ひな型）から実テキストを入れる。ひな型が `[○○を入れてください]` のままの箇所は、Deck Info とスライドtypeから自然な内容を補って埋める。

### 出力ファイルの命名と保存先

各スライドを次のパスに保存する（**2桁ゼロ埋め**、スライド番号に一致）：

    SLIDE-DECK/SLIDE-DECK-{name}/slides/slide-01.html
    SLIDE-DECK/SLIDE-DECK-{name}/slides/slide-02.html
    ...

`slides/` フォルダが無ければ司令塔がSTEP 3開始時に作成しておく。サブエージェントには絶対パスで指示し、1エージェントが複数枚担当する場合はそれぞれのパスを列挙する。

## STEP 4：検品（司令塔の仕事）

全バッチのサブエージェントが完了したら、司令塔が仕上がりを点検する。**ここでも司令塔は全HTMLを精読しない**（コンテキストを守るため、機械的チェックとサンプリングに留める）。

1. **ファイル数と連番のチェック**：`slides/` 内の `slide-*.html` を一覧し、枚数が `slide_count` と一致するか、`slide-01` から連番で**欠落が無いか**を確認する。欠けている番号があれば控える。
2. **サンプル読みによるトークン一致確認**：全体から数枚（例：先頭・中間・末尾の3枚程度）を Read し、`<style>` 内の Primary色・ベースフォント・スライドサイズがSTEP 2で控えたDesign Systemの主要トークンと一致するかを確認する。スケルトンのダミー色（`#E8E8E8`・`#888` 等）が残っていないかも見る。
3. **再生成**：欠落したスライド、またはサンプルでトークン不一致が見つかったスライドについては、**そのスライドだけ**をサブエージェント（`model: "sonnet"`）に再生成させる。指示内容はSTEP 3と同じ（該当スライドの行範囲＋Design Systemの行範囲＋パターンの行範囲＋出力パス）。不一致が見つかった場合は「グレーのダミー色ではなくDesign Systemの色を使うこと」を明示的に付け加える。全体の作り直しはしない。

問題が無ければSTEP 5へ進む。

## STEP 5：ビューア生成と提示

一覧ビューアと印刷用ページを司令塔が生成する（これらは定型なので司令塔が直接書いてよい）。

### 一覧ビューア `slides/index.html`

全スライドをサムネイルで一覧表示する。各サムネイルは**スライドHTMLをiframeで縮小埋め込み**し、クリックすると原寸（別タブ）で開く。JavaScriptは使わずiframe＋CSSで完結させる。サムネイルの実装例：

    .thumb { width: 480px; height: 270px; overflow: hidden; position: relative;
             border: 1px solid #DDD; border-radius: 8px; background: #FFF; }
    .thumb iframe { width: 1920px; height: 1080px; border: 0;
                    transform: scale(0.25); transform-origin: top left; pointer-events: none; }

各サムネイルは `<a href="slide-01.html" target="_blank">` で原寸表示にリンクし、下にスライド番号とタイトルを添える。iframe の `src` は同階層の相対パス（`slide-01.html` 等）でよい。

### 印刷用ページ `slides/print.html`

ブラウザの印刷機能でPDF化するためのページ。全スライドを1920×1080のページとして**縦に連結**し、`@page` とページブレークを設定する：

    @page { size: 1920px 1080px; margin: 0; }
    .page { width: 1920px; height: 1080px; overflow: hidden; page-break-after: always; }
    .page:last-child { page-break-after: auto; }
    .page iframe { width: 1920px; height: 1080px; border: 0; }

各 `.page` に該当スライドHTMLをiframeで等倍埋め込みし、順番に並べる。印刷ダイアログで「用紙サイズをスライドに合わせる／余白なし／背景グラフィックあり」を選ぶとスライド1枚＝1ページのPDFになる。

### ローカルサーバー配信の案内

`index.html` と `print.html` はどちらも別のローカルHTMLファイルをiframeで読み込む構成のため、`file://` で直接開くと**ブラウザのセキュリティ制限によりiframeの中身が空白になる**。表示確認は必ず `http://` 経由で行う。`slide-deck-builder` と同様に `.claude/launch.json` によるローカルサーバー配信を用意する：

1. カレントディレクトリの `.claude/launch.json` を確認し、カレントディレクトリ全体を配信する設定が無ければ追記する（既存設定は消さず末尾に追加）。無ければ新規作成する：

       {
         "version": "0.0.1",
         "configurations": [
           {
             "name": "slides-root",
             "runtimeExecutable": "python3",
             "runtimeArgs": ["-m", "http.server", "{空いているポート番号}", "--directory", "{カレントディレクトリの絶対パス}"],
             "port": {空いているポート番号}
           }
         ]
       }

2. サーバーを起動し、`http://localhost:{port}/SLIDE-DECK/SLIDE-DECK-{name}/slides/index.html` を開いて表示を確認する。
3. ユーザーへの提示時も、直接ファイルを開くのではなくローカルサーバー経由で開くよう明記する。

HTMLプレビュー機能が使える環境（Claude Code のプレビュー等）では、上記サーバーを起動した上で該当URLをそのまま開いてよい。

## 完了通知

すべて完了したら、以下の形式でユーザーに伝える：

> 「`SLIDE-DECK/SLIDE-DECK-{name}/slides/` にHTMLスライド [N] 枚を生成しました。
>
> **生成物：**
> - `slides/slide-01.html` 〜 `slides/slide-{NN}.html`（各スライド、1920×1080・自己完結HTML）
> - `slides/index.html`（サムネイル一覧。クリックで原寸表示）
> - `slides/print.html`（PDF化用ページ）
>
> **確認方法：**
> ローカルサーバー『slides-root』を起動し、`http://localhost:{port}/SLIDE-DECK/SLIDE-DECK-{name}/slides/index.html` を開いてください（`file://` で直接開くとサムネイルが空白になります）。
>
> **PDF化：**
> `print.html` を同じくサーバー経由で開き、ブラウザの印刷（Cmd/Ctrl+P）→ 保存先「PDF」→ 用紙サイズをスライドに合わせ・余白なし・背景グラフィックありにすると、スライド1枚＝1ページのPDFになります。
>
> **修正したいとき：**
> 「Slide 3 の見出しを○○に変えて」のように**スライド番号を指定**して伝えてください。該当スライドだけを作り直します。」

## 修正サイクル（個別スライドの再生成）

ユーザーから特定スライドの修正指示（例：「Slide 3 の見出しを変えて」「Slide 7 のグラフの色をPrimaryに」）が来たら：

1. 司令塔が該当スライドの `### Slide N` 仕様と、そのスライドが使うパターン定義・Design System の行範囲を再確認する（STEP 2の対応表を使う）。
2. **該当スライド1枚だけ**をサブエージェント（`model: "sonnet"`。複雑なチャートを含む場合のみ `opus`）に再生成させる。渡す情報はSTEP 3と同じ最小セット（設計書パス＋該当行範囲＋出力パス）に、ユーザーの修正指示を1行加える。
3. 出力先は元と同じ `slides/slide-{NN}.html`（上書き）。`index.html` と `print.html` はファイル名を参照しているだけなので再生成不要。

**全体の作り直しはしない。** 修正は常に該当スライド単位に限定し、司令塔のコンテキストとトークンを守る。複数スライドの修正依頼が同時に来た場合は、それらをまとめて数枚ずつのバッチにし、STEP 3と同じ要領で並列再生成してよい。
