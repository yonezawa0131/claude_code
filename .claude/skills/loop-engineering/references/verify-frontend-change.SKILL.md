# verify-frontend-change(検証: turn-based loop の自己検証を強化する雛形)

これは turn-based loop(毎プロンプトで回る素のエージェントループ)の**検証ステップを skill に encode して自己検証を強化する**ための雛形。別エージェントによる敵対的レビュー(`reviewer.md` 的なもの)とは別物で、こちらは"生成エージェント自身に人間のQA手順を踏ませる"軽量パターン。reviewer を立てる余裕がない/立てるまでもない粒度の変更で使う。

このファイル自体はテンプレートであり、`# change:` コメントの箇所を自プロジェクトの実値に置き換えてから使うこと。

## 前提

編集が成功した(diffが意図通り・lint/typecheckが通った)ことは、UIが意図通り動くことの証明にならない。以下の4手順をすべて通過するまで、UI変更を完了と報告してはならない。どこかで失敗したら直して手順1からやり直す。**部分的にしか検証していない仕事を返さない。**

## 手順

1. **dev serverを起動し、編集したページをブラウザで開く**
   <!-- change: 自プロジェクトの dev server 起動コマンドに置き換える。例: `npm run dev`, `pnpm dev`, `bin/rails server` -->
   ```bash
   npm run dev
   ```
   <!-- change: 対象URL/ページに置き換える。例: http://localhost:3000/settings -->
   起動後、変更が反映されたページ(`http://localhost:3000/<対象パス>`)を開く。

2. **変更を直接操作する**
   新しいコントロール(ボタン・入力・トグルなど)を追加/変更した場合:
   - そのコントロールをクリック/入力操作する
   - 期待した状態変化(表示切り替え・値の更新・画面遷移など)が実際に起きることを確認する
   - 操作前(before)と操作後(after)のスクリーンショットを撮る
   <!-- change: 使用する検証ツールに置き換える。例: Playwright MCP、Chrome DevTools MCP -->
   ここでは Playwright MCP(または Chrome DevTools MCP)のブラウザ操作ツールを使い、実ブラウザ上での操作として行う。目視確認やコード読解による「推測」で代替しない。

3. **ブラウザコンソールを確認する**
   <!-- change: コンソール取得に使うツールに置き換える。例: Chrome DevTools MCP の console 取得系ツール、Playwright MCP の console イベント -->
   変更前後でコンソールログを取得し、新規のエラー・警告が **ゼロ件** であることを確認する。既存の(この変更と無関係な)警告は許容するが、変更に起因する新規エラーが1件でもあれば手順1からやり直す。

4. **パフォーマンス監査を行う**
   <!-- change: Chrome DevTools MCP のperformance trace系ツール名に置き換える -->
   Chrome DevTools MCP を使い、対象ページで performance trace を実行し Core Web Vitals(LCP・CLS・INP など)を監査する。変更によって既存のスコアが悪化していないかを数値で確認する。

## 失敗時の扱い

- 手順1〜4のいずれかで失敗(エラー・警告の発生、期待した状態変化が起きない、スコアの悪化)した場合は、修正してから手順1に戻ってやり直す。
- 「一部だけ確認できた」状態でループを止め、完了として報告してはならない。

## 補足: 検査は定量的なほど自己検証しやすい

「見た目が正しそうか」のような主観的・曖昧な合否基準は、エージェント自身にとって判定が難しく、自己検証の質を下げる。可能な限り数値基準に落とすこと(例: コンソールエラー0件、テストn件green、Lighthouse/Core Web Vitalsのスコアが閾値以上、before/afterのスクリーンショット差分が意図した範囲内)。基準が数値であるほど、エージェントは「合格/不合格」を自分で機械的に判定でき、次の一手(直してやり直す/完了報告する)を誤らない。
