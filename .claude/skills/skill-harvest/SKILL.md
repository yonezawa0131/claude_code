# skill-harvest（成功パターンのスキル昇格）

同種のタスクを毎回ゼロから試行錯誤するのは知識の揮発。うまくいった手順を
Skill として抽象化し、次回から自動発火で再利用する。memory-dream が
「宣言的知識（事実・ルール）」の整理なら、こちらは「手続き的知識（手順）」の資産化。

## 昇格の基準（全部満たすときだけスキル化する）

1. **3回以上**同種のタスクをこなし、確立した手順がある（1回の成功では抽象化しない — 偶然かもしれない）
2. 手順が**プロジェクト非依存に一般化できる**（特定ファイルパスや一時的な事情に依存しない）
3. 既存 Skill・ハーネス標準機能（/verify, /code-review 等）と**重複しない**。
   近い Skill があるなら新設せずそちらを拡張する
4. 手順に**判断が含まれる**こと。単なるコマンド1発なら Skill でなく
   settings.json の permissions や alias で足りる

## スキルの3分類（どれに当たるか先に決める)

- **Prompt Skill**: 検証済みプロンプト・観点リストの再利用（例: 特定形式のレビュー観点）
- **Workflow Skill**: 複数ステップの手順書。順序・依存・失敗時の分岐を持つ（例: memory-dream）
- **Code Skill**: 再利用可能なスクリプトを `scripts/` に置き、Skill から使い方を指す
  （例: claude_export_to_obsidian.py）

## 手順

1. **Mine**: 直近の作業から「また同じことをやった」パターンを特定する。
   何がトリガーで、何を入力に、どういう順序で、何を成果物にしたかを書き出す。
2. **Abstract**: 具体値をパラメータ化する。今回のタスク固有の値（企業名・パス・日付）を
   `{変数}` に置き換え、どんな入力にも通じる形の手順にする。
   一緒に**失敗から学んだ回避策**も手順に織り込む（エラーは資産）。
3. **Dedup**: 既存の `.claude/skills/` と個人 Skill を確認し、重複・近接がないか見る。
   近接があれば新設せず既存 Skill に節を足す。
4. **Write**: SKILL.md を書く。frontmatter の description が発火条件のすべてなので、
   **トリガーになる言い回しを具体的に列挙する**（memory-dream の description を手本にする）。
   本文は「いつ使うか/使わないか」「手順」「チェックリスト」の順。
5. **Review**: 論理単位で commit してユーザーレビューに出す（push は保留）。
   Skill は毎セッション読み込まれうるため、採用前レビュー必須。

## 書き方の原則

- description に発火トリガー（ユーザーが言いそうなフレーズ）を必ず入れる。
  トリガーのない Skill は存在しないのと同じ。
- 本文に経緯・失敗談・セッション ID は書かない（memory-dream の
  「成果ファイルの書き方」と同じ原則）。現行で正しい手順だけ残す。
- 「使わない場合」を必ず書く。誤発火は Skill の信頼を下げる。
- 置き場所: このリポジトリ固有なら `.claude/skills/`、全プロジェクト共通なら
  個人 Skill（~/.claude/skills/。リモート環境では sync-personal-skills.sh の仕組みに載せる）。

## メンテナンス

- 使うたびに手順とのズレに気づいたら、その場で SKILL.md を直して commit する
  （使用実績が更新のトリガー）。
- 3ヶ月使わなかった・前提が消えた Skill は memory-dream 実施時に削除候補として挙げる。
