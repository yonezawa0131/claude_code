# session-compound(セッション成果の書き戻し)

自己改善システムの複利は「層 3(記憶)への書き戻し」で閉じる — 書かずに終えたセッションの次はゼロから再出発になる(設計は `notes/playbook/self-improving-system.md` 原則 3・4 を参照。このSkillでは再掲しない)。このSkillは同 playbook の運用律 **Write before walking away** をセッション終了時の定型手順にしたもの。日次の vault-compile(raw/ 新着の整理)とは対象が違う: こちらは **いま終わろうとしているセッション自体** から教訓を抽出して書き戻す。

## 前提: 書き戻し先の特定

1. Obsidian vault を運用している場合(構造は `notes/playbook/obsidian-vault.md`)→ vault が書き戻し先。場所の解決手順は vault-compile Skill の「前提」に従う。
2. vault が無いプロジェクト → プロジェクトルートの `STATE.md`(無ければ 5 セクション構成で新規作成: Verified facts / General rules / Open failures / Lessons learned / Last session)。
3. どちらとも判断できなければ推測で進めず、ユーザーに確認する。

## 手順

1. **抽出**: このセッションを振り返り、次を列挙する — (a) 確定した事実・方針、(b) 失敗と、その調査・検証がどこまで済んだか、(c) 一般ルールに蒸留できる教訓、(d) 未解決のまま持ち越す仮説、(e) 次セッションの再開ポインタ(何をどこまでやったか・次の一手)。一回限りのデバッグメモは拾わない(memory-dream Mine フェーズと同じ基準)。
2. **段階判定(最重要)**: 各項目を 5 段階記憶(fail → investigate → verify → distill → consult)のどこまで到達したかで仕分ける。**検証していない推測を「検証済みの事実」として書かない。** 推測は推測の置き場(NOW.md「未解決の仮説」/ STATE.md「Open failures」)へ、検証済みだけを事実・ルールの置き場へ。
3. **書き戻し先の振り分け**:
   - プロジェクト固有の検証済み事実・ルール → vault の entities/ concepts/(出典リンク付き)/ STATE.md の Verified facts・General rules
   - 未解決の仮説・持ち越しの失敗 → NOW.md「未解決の仮説」/ STATE.md の Open failures
   - 再開ポインタ → NOW.md「直近の決定」(20 行以内を維持)/ STATE.md の Last session
   - **作業の種類に紐づく手続き的教訓 → 該当 Skill 自体に書き戻す**(次項)
4. **Skill への書き戻し**: 教訓が「この種の作業のやり方」ならプロジェクト記憶でなく該当 Skill の **Known failure modes(既知の失敗モード)/ Anti-patterns(やってはいけないこと)** 節へ追記する(節が無ければ作る)。該当 Skill が存在しない教訓が複数セッションで繰り返されているなら、新 Skill の作成を提案する(勝手には作らない)。定義は 1 箇所 — vault/STATE 側には Skill へのポインタだけ残す。
5. **書き込みルールの遵守**: vault へ書く場合は playbook の書き込みルールに従う(1 ファイル 1 教訓・重複ページ禁止・バックリンク 3 本以上・出典規律・タグ固定スキーマ・raw/ 不可侵)。
6. **独立検証**: 書き込んだ内容を、このセッションの推論過程を渡していない検証 subagent(安価なモデルでよい)に見せ、「検証済みとして書かれた項目に根拠・出典があるか」「推測が事実の置き場に混入していないか」をチェックさせる。指摘があれば修正してから確定する。
7. **提示規律**: 変更は diff で提示し、論理単位ごとに commit できる粒度に分ける。push はユーザー明示指示まで保留する。

## Known failure modes

(このSkill自身も複利対象。実際の失敗から追記していく)

- 書き戻しをセッションの「余力があれば」に回すと実行されない。大きな作業の完了直後・コンテキストが新鮮なうちに回す。
- 検証 subagent に層の違う対象(compiled ページ・ルートページ・raw)を一括で渡すと、compiled 規律をルートページに誤適用した偽陽性を出す(2026-07-08 に実例)。ルーブリックには対象ごとの適用範囲を明記し、検証者の指摘は採用前にレビューする。

## Anti-patterns(やってはいけない)

- 未検証の推測を Verified facts / concepts に書く(複利するのは検証済みだけ。推測の混入は memory-dream での除去コストになる)
- 経緯・履歴(誰がいつ指摘したか・失敗談の物語)を成果ファイルに書く(memory-dream「成果ファイルの書き方」に従い、残すのは現行で正しい知見だけ)
- 同じ教訓を vault と Skill の両方にフル記載する(定義は 1 箇所、他方はポインタ)
- raw/ への書き込み(不可侵)

## チェックリスト

- [ ] 確定事項・失敗・教訓・仮説・再開ポインタを漏れなく抽出した
- [ ] 各項目を 5 段階で仕分け、推測と検証済みを分離した
- [ ] 手続き的教訓を該当 Skill の Known failure modes / Anti-patterns に書き戻した
- [ ] vault の書き込みルール(リンク・出典・タグ・raw/ 不可侵)を守った
- [ ] NOW.md / Last session を更新した(NOW.md は 20 行以内)
- [ ] 独立検証 subagent のチェックを通した
- [ ] 変更を diff で提示し、論理単位ごとに commit 可能(push は保留)
