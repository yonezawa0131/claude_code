# long-task-state（長時間タスクの状態管理）

長時間実行タスクの5大リスク — コンテキスト溢れ・途中失敗・コスト超過・
再開位置の喪失・当初目標からの逸脱（ドリフト） — に、作業ディレクトリ直下の
`STATE.md` 1ファイルで対処する運用。

## いつ使うか / 使わないか

- 使う: フェーズが3つ以上、想定30分超、外部要因（ネットワーク・API制限・
  セッション切断）で中断しうる、または「後で再開する」可能性があるタスク。
- 使わない: 1〜2ステップで完結するタスク。STATE.md 自体がノイズになる。

## STATE.md のフォーマット（lean に保つ）

```markdown
# STATE.md — {タスク名}

## ゴール（開始時に書き、以後変更しない）
{ユーザーの依頼を原文に近い形で。ドリフト判定の基準になる}

## ステータス
- 更新: {絶対日時}
- フェーズ: {現在フェーズ} ({n}/{総数})
- 予算: {使った量} / {上限}（トークン・API費用・時間など該当するもの）

## 完了フェーズ
- [x] phase_1: {成果物の場所} ({完了時刻})
- [ ] phase_2: {進行中。部分成果の場所}

## チェックポイントデータ
{再開に必要な最小限: 処理済みアイテムのリスト、部分出力のパス、次の入力}

## エラー・スキップ記録
- {時刻} {何が失敗し、どう対処したか（リトライ/スキップ/代替）}
```

肥大化させない。会話ログや思考過程は書かない。「再開に必要な事実」だけ。

## 運用ルール

1. **チェックポイントはフェーズ境界ごと**に STATE.md を更新する。
   並列処理ではアイテム完了ごと（例: 10社分析なら1社ごと）に完了リストへ追記。
2. **再開時は STATE.md を最初に読む。** 完了フェーズは再実行せず、
   チェックポイントデータから続きを始める。部分成果ファイルの実在を確認してから使う。
3. **失敗は記録して続行**（skip_and_continue）が基本。ただし同一ステップで
   3回失敗したら止めてユーザーへ報告する。エラー記録は消さない — 失敗パターンは資産。
4. **予算を開始時に決める。** 上限の8割で警告として STATE.md に記し、
   上限到達で作業を止めてユーザーに判断を仰ぐ。上限なしで回さない。
5. **ドリフトチェック**: フェーズ完了ごとに「ゴール」節を読み直し、
   直近の成果がゴールに向かっているか自問する。逸脱していたら勝手に軌道修正せず、
   STATE.md に逸脱内容を書いてから修正方針を決める（大きな逸脱はユーザー確認）。

## 検証ゲート（非コード成果物にも）

コードは `/verify` `/code-review` があるが、分析・文章などの成果物も
フェーズ末に自己検証する。生成した直後の視点ではなく、検証者の視点で:

- 事実: 数字・固有名詞・引用に根拠があるか（持ち込み情報は出典と突き合わせる）
- 論理: 前提→結論が飛んでいないか
- 網羅: 依頼された項目をすべて満たしたか
- 中間成果は7割、最終成果物は9割を目安に、満たさなければ改善して再検証（最大3回。
  超えたら最良版を提示してユーザーへエスカレーション）

## エスカレーション条件（自動で進めてはいけない判断)

以下に当たったら作業を止め、状況を STATE.md に固定してからユーザーに報告する:

- 予算上限（またはその9割）到達
- 同一ステップの最大リトライ超過
- 未知のタイプのエラー（分類できない失敗）
- ゴールの解釈が分かれる分岐・スコープ変更を伴う判断
- ユーザーデータの破壊的変更・外部公開を伴う操作
