# 検証器の検証と、検出できる下限

`docs/03` で「検出器が壊れていないこと」を確かめた。
ここでは残り2つを測る。

1. **判定器は壊れていないか** — ウォークフォワード検証は、優位性の消滅を捉えられるか
2. **どこまで弱い信号を拾えるか** — 検出できる下限はどこにあるか

どちらも合成データだけで測れる。実データは要らない。

---

## 1. ウォークフォワード検証は、死んだ優位性を弾けるか

### 測り方

`intraday` レジームに `--intraday-beta-end` を足した。
埋め込む強さがセッションごとに線形に変化する。

```bash
# 優位性が期間の後半にかけて裁定されて消えていくデータ
python scripts/make_synthetic.py --bars 20000 --seed 3 --regime intraday \
  --intraday-beta 1.0 --intraday-beta-end 0.0 --out data/decaying.csv
```

これは実際に起きること。公表された異常収益は縮小する傾向がある。
そして厄介なことに、**全期間で1回バックテストすると気づけない。**

### 分かったこと（10シード・20000本・6分割）

| | 全期間で1回測ると | 勝った期間 | 後半 − 前半 |
|---|---|---|---|
| 優位性が一定 | **+288%** | 6.0 / 6 | +0.98 pt |
| 優位性が消滅 | **+38%** | **4.2 / 6** | **−17.53 pt** |

**消滅しているのに、全期間では +38% でプラスに見える。**
前半の利益が後半の損失を覆い隠している。

そして問題は次だった。**当時の実装は、これを警告なしで通していた。**

`summary()` は「勝った期間が過半数以下」でのみ警告を出していた。
消滅データでも4/6は勝つので、10シード中9回で警告が出ない。

原因は単純で、**数え上げは順番を捨てるから**。
前半の貯金があれば、死んでいても過半数は残る。

### 直したこと

順番を見る統計量を2つ足した。

**decay_z** — 後半の平均が前半よりどれだけ悪いかを、期間リターンの標準偏差で割った値。
標準化するのは、リターンそのもので閾値を切ると
**優位性が大きい戦略ほど誤検知しやすくなる**ため。

| | decay_z の範囲（10シード） |
|---|---|
| 優位性が一定 | −0.95 〜 +1.43 |
| 優位性が消滅 | **−1.75 〜 −1.09** |

閾値 −1.0 で 10/10 ずつ正しく分かれる。
**ただし境目に余裕はほとんどない**（一定側の最悪 −0.95 と消滅側の最良 −1.09 が隣接）。
この数字ひとつで採否を決めてはいけない。

**最終期間が負なのに全体が正** — こちらは 0/10 対 10/10 で完全に分かれた。
単純だが、「測っているのは過去の相場であって今の相場ではない」ことに
気づける最も確実な手がかりになる。

### 期間あたりの取引数という前提

最初に 8000本を6分割して測ったとき、**一定と消滅の区別がつかなかった**。
各期間28回の取引しかなく、ノイズに埋もれていた。

`metrics.evaluate()` は取引30回未満で警告を出す。同じ基準が
ウォークフォワードの各期間にも要る。→ 期間ごとの取引数が30回を切ったら警告するようにした。

**足りないときに「足りない」と言えることは、答えを出すことと同じくらい重要。**

## 2. 検出できる信号の下限

`beta=1.0` は「検出できて当然」の強さにしてあった。
実際の効果がこれより弱ければコストに埋もれる。どこまでなら拾えるのか。

### 結果（5シード平均・20000本・約420トレード）

| beta | 1トレードの粗利 | 成行（Taker） | 指値（Maker） | コストゼロ |
|---|---|---|---|---|
| 0.00 | 0.0 bp | −50.8% | −3.0% | +5.6% |
| 0.10 | 4.8 bp | −39.4% | +19.5% | +30.1% |
| 0.20 | 9.6 bp | −25.4% | +47.2% | +60.3% |
| 0.30 | 14.4 bp | −8.1% | +81.3% | +97.4% |
| **0.376** | **18.0 bp** | **分岐点** | | |
| 0.50 | 23.9 bp | +39.4% | +175.3% | +199.7% |
| 1.00 | 47.9 bp | +296.0% | +683.3% | +753.1% |

分岐点は算術で出る。ロングだけ取る場合の1トレードの粗利の期待値は

```
beta × sigma × sqrt(2/π)
```

これが往復コストを超えたところが分岐。

| 執行 | 往復コスト | 必要な粗利 | 必要な beta |
|---|---|---|---|
| 成行（Taker） | 0.180% | **18.0 bp** | 0.376 |
| 指値（Maker） | 0.020% | **2.0 bp** | 0.042 |

**実測もここで反転した**（成行は beta=0.34 で −0.1%、0.38 で +8.5%）。
算術と実測が一致したので、エンジンのコスト計上は正しい。
これは戦略の検証というより**エンジンの検算**にあたるので、テストに固定した
（`test_breakeven_matches_the_cost_arithmetic`）。

### 読み取れること

**執行方法が、検出できる信号の下限を9倍変える。**

指標を選び直すことでは、この差は埋まらない。
`docs/02` の項目2（成行より指値）は「コストが下がる」という話だったが、
本当の意味は**そもそも検出できる仮説の範囲が変わる**ことにある。

成行で回す限り、18bp未満の優位性は存在しても取れない。
そして**日中の値動きの予測可能性が18bpを超えるかどうかは、事前には分からない。**

### この数字の限界

**指値の側は上限値であって、実現値ではない。**
現在のエンジンは「指値を並べたら必ず約定する」前提で計算している。
実際には、指値が約定するのは価格が自分に向かってきたとき＝不利な側であることが多く
（逆選択）、約定しなかった取引は機会損失として消える。

つまり 0.042 という下限は、**達成可能な最良の場合**にすぎない。
約定確率のモデル化は未実装で、これが次の課題になる。

## まとめ：今どこまで言えるか

**言える**
- 検出器は、存在するパターンを検出できる（`docs/03`）
- 検出器は、存在しないパターンを見つけたと言わない（`docs/03`）
- 判定器は、優位性の消滅を捉えられる（decay_z と最終期間の符号）
- 成行で回すなら、18bp以上の優位性でなければ取れない
- 期間あたり30回の取引がなければ、傾向は読めない

**言えない**
- 実データに日中モメンタムがあるか。**まだ測っていない**
- あったとして、それが18bpを超えるか
- 指値が実際に約定するか（未実装）

道具は揃った。**対象にはまだ何も触れていない。**
