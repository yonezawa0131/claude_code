# GMOコイン API 接続手順

## 出どころについて先に断っておく

この開発環境からは `api.coin.z.com` にも `coin.z.com` にも到達できない
（プロキシが遮断する）。**公式ドキュメントを直接読めていない。**

だから仕様は、独立した複数の実装・記事を突き合わせて確定させた。
確度は3段階に分かれる。

| 確度 | 内容 | 根拠 |
|---|---|---|
| **高** | 署名の作り方、エンドポイント、本文の項目名 | 稼働実績のあるクライアント実装のソースコード |
| **中** | 手数料率、銘柄の対応 | 複数の二次情報が一致 |
| **低** | 会員ページの画面上の文言 | **確認できていない。画面を見て読み替えること** |

最小注文数量と刻み幅は、**こちらで持たずに取引所から読む**ようにした
（`/public/v1/symbols`）。記憶で持つと、取引所が変えた日から嘘になる。

**この判断は初回の実行で報われた。** 二次情報にあった BTC の最小注文数量は
0.0001 だったが、取引所が返した実際の値は **0.00001**（10分の1）だった。
記憶で持っていたら、確認のために10倍の額を動かしていた。

## 実行済み：読み取り側は取引所に受理された

2026年8月4日、実口座に対して `--check-connection` を実行した。

| 段階 | 結果 |
|---|---|
| 0. 取引所の状態 | OPEN |
| 1. 公開API（署名なし） | **OK** — BTC/JPY 10,035,200 円 |
| 2. 私設API（署名あり） | **OK** — 取引所が署名を受理した |
| 3. 発注本文 | 組み立てのみ。送っていない |

**これで確定したこと。** 鍵・時刻（ミリ秒）・HMAC-SHA256・ヘッダ名
（`API-KEY` / `API-TIMESTAMP` / `API-SIGN`）・署名するパスから `/private` を
除くこと。**署名の組み立ては正しい。**

**これで確定していないこと。** 口座に資産が無かったため、資産の応答は
空で返った。空の応答は次の2つを区別できない。

1. 口座に資産がない（正しく読めている）
2. 応答の解釈を間違えていて、何も拾えていない

**入金してからもう一度実行し、金額が画面と一致して、はじめて読み取り側が
確かめられる。** `--check-connection` は資産が空のとき、そう表示する。

## 手順

### 1. 口座を開く

本人確認まで済ませる。APIキーの発行は**ブラウザの会員ページからのみ**で、
スマートフォンアプリからはできない。

### 2. 「取引所（現物）」を使うことを確認する

GMOコインには**販売所**と**取引所**があり、別物になる。

| | コスト | API |
|---|---|---|
| 販売所 | **スプレッドで片道3〜6%** | 使える |
| **取引所（現物）** | **Maker −0.01% / Taker 0.05%** | 使える |
| レバレッジ | 建玉に**1日0.04%**、上限2倍 | 使える |

**販売所は短期売買では絶対に使わない。** 往復6〜12%は、この基盤が測った
どの戦略でも取り返せない。`run_live.py` は取引所（現物）に発注する。

手数料は BTC・ETH・XRP・DAI が Maker −0.01% / Taker 0.05%、
それ以外は Maker −0.03% / Taker 0.09%（**二次情報。画面で確認すること**）。

### 3. APIキーを作る

会員ページの「暗号資産 API」から発行する。発行時に**機能ごとの権限**を選べる。

> **出金・送金の権限は付けないこと。**
>
> この基盤が使うのは「資産照会」と「注文」だけになる。
> 出金権限を付けた鍵が漏れると、資産を持ち出される。付けなければ、
> 最悪の場合でも**動かされるのは板の上だけ**になる。
>
> 権限の項目名は画面で確認すること（ここでは確認できていない）。
> 迷ったら、**まず全部オフにして、通らなかったものだけ足す**。
> `--check-connection` は資産照会だけで通るので、切り分けに使える。

接続元IPを制限できるなら、実行するマシンのIPを入れておく。

### 4. 鍵を環境変数で渡す

```bash
export GMO_API_KEY='...'
export GMO_API_SECRET='...'
```

**ファイルに書いてリポジトリに置かないこと。** `.env` を作るなら
`.gitignore` に入っていることを確認する。

### 5. つながるか確かめる（**1円も動かさない**）

```bash
.venv-trading/bin/python trading/run_live.py --check-connection --exchange gmo
```

出るのは4つ。

```
0. 取引所の状態 — OPEN
1. 公開API（署名なし）— 価格が取れるか
2. 私設API（署名あり）— 鍵・nonce・HMAC・応答の解釈
3. 発注本文 — 組み立てるだけで、送りません
```

**2で出る残高を、取引所の画面と突き合わせること。** 合わなければ応答の
解釈が間違っている。合えば、鍵と署名は正しいと確定する。

`0.` を見るのは、**GMOコインに定期メンテナンスがある**ため。その最中の
失敗は配線の問題ではない。切り分けられないと、直っているものを直そうとする。

### 5.5. 資産が空で返ったら、まだ確かめられていない

口座に資産が無いと、応答は空で返る。**これを「読めた」と数えてはいけない。**
空の応答は「資産がない」と「解釈を間違えて何も拾えていない」を区別できない。

入金してからもう一度実行し、**金額が画面と一致すること**を確認する。
そこまでやって、はじめて読み取り側が確かめられる。

### 6. 残るのは1つだけ

読み取りが通れば、未検証なのは「**発注したときの応答の解釈**」だけになる。
署名の仕組み（時刻・HMAC・ヘッダ名）は読み取りと発注で共通だからになる。

そこまで確かめるなら、`3.` で表示された本文を1回だけ送り、

- 取引所の画面に**同じ数量・同じ価格で並んでいること**を確認し
- **すぐ取り消す**

約定しない位置の指値なら、これで損失は出ない。

## bitbank と違っていて、間違えると金が減るところ

実装で3つ踏んだ。どれも**エラーにならずに通ってしまう**種類になる。

### 1. 銘柄名 — `BTC` は現物、`BTC_JPY` はレバレッジ

```
BTC      → 現物。買えば現物を持つ
BTC_JPY  → レバレッジ。建玉であって現物ではない
```

出回っているサンプルコードには `symbol='BTC_JPY'` で発注しているものがある。
そのまま真似すると、**現物を買ったつもりでレバレッジ建玉を持つ**。
建玉には1日0.04%かかるので、持っているだけで負けが積み上がる。

`GmoBroker` は対応表にある現物銘柄しか受け付けず、`BTC_JPY` を渡されたら拒否する。

**そしてこの防御を書いたとき、自分で逆向きに壊した。** 照合を
`pair.upper() in レバレッジ銘柄` と書いたせいで、内部表記の `btc_jpy` が
`BTC_JPY` に化けて、**全銘柄が拒否された**。綴りが同じで指すものが違うので、
照合は大文字のまま完全一致でやる必要がある。

### 2. 署名するパスに `/private` を含めない

```
リクエスト先  https://api.coin.z.com/private/v1/account/assets
署名する文字列 1700000000GET/v1/account/assets
                          ^^^^^^^^^^^^^^^^^^^ /private が無い
```

GET のクエリ文字列も署名に含めない。

### 3. 数量を指数表記で送らない

```
str(0.00001)  →  '1e-05'   ← 送ると弾かれる
```

GMO の BTC 現物の最小注文数量は **0.00001**。つまり
**最小数量で出すたびに指数表記になる**。「一番小さい注文から順に試す」のは
確認の手順として一番やりたいことなので、そこだけ通らないのが一番たちが悪い。

しかも症状は「署名は通るのに注文だけ弾かれる」になる。署名を疑って探し回ることになる。

`plain_decimal()` を通してから送る。接続確認の出力にこの形が出て、**送る前に気づいた。**

### 4. HTTP 200 でも失敗していることがある

```json
{"status": 1, "messages": [{"message_code": "ERR-5106", "message_string": "..."}]}
```

`status == 0` が成功になる。見ないと、**失敗した注文を成功として記録する**。
記録が嘘になると、次の実行が誤った現在地から始まる。

## これで何が変わるか

**優位性の話は1ミリも進んでいない。**

つながることと、儲かることは別になる。この基盤は7つの仮説を検定して、
6つを否定し、1つは検定する手段がなかった。合格記録のある戦略は**まだ無い**。

だから `--live` を付けても、関門が止める。

```
[未検証] 戦略「equal_weight_btc」の検証記録がありません。
```

接続確認で片付くのは「配線の不安」だけになる。片付けておく価値はある
—— 動かす日が来たときに、戦略の問題と配線の問題を同時に切り分けずに済む。

`docs/08` の結論は変わらない。目標に近づく確実な手段は**元本と税制**であって、
接続はその手段を実行するための道具にすぎない。
