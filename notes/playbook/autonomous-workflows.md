# 自律ワークフロー基盤（autonomous workflows）

Claude を「話しかける相手」ではなく「不在時に境界内で動き、成果物を残すシステム」として運用するための基盤。元ネタは「60 の自律ワークフロー」記事の共通構造:

> すべてのワークフローは **トリガー + エージェント + 検証** の 3 部構成。
> 検証を省くと、無人で高くつくミスが走る。トリガーを省くと、結局すべて手動起動に戻る。

## アーキテクチャ

```
トリガー                Fable（司令塔）              実行層                検証層
─────────           ─────────────────         ─────────────        ──────────────
cron / Routine  ──▶  workflows/*.md を読む ──▶  executor-sonnet  ─▶  verifier(読取専用)
ファイル投入           計画・分担・境界の強制        executor-opus         + 機械的チェック
手動 /autopilot       最終ゲート・報告・ログ        triage(haiku)             │
                          ▲                                              │
                          └───── FAIL なら差し戻し（最大1回）─────────────┘
```

### 役割分担（モデル階層）

| 役割 | モデル | 担当 | やらないこと |
|---|---|---|---|
| 司令塔 | **Fable**（メインセッション） | ワークフロー解釈、タスク分割、dispatch、検証結果の最終判断、ユーザーへの報告 | 実作業（ファイル大量編集・長い調査）を自分でやらない |
| 実行 | **executor-opus** | 複雑・多段・判断を要する作業（デバッグ、リファクタ、長文統合） | 検証の自己申告（自分の成果を自分で合格にしない） |
| 実行 | **executor-sonnet** | 仕様が明確な定型作業(要約、整形、索引同期、下書き生成) | 仕様の再解釈・スコープ拡大 |
| 分類 | **triage**（haiku） | 安価な一次分類・ルーティング。確信がなければ上位へエスカレーション | 実作業 |
| 検証 | **verifier**（opus・読取専用） | 成果物をワークフローの受け入れ基準と照合し PASS/FAIL 判定 | 修正(書き込みツールを持たない) |

原則: **作る者と検証する者を分ける**（maker-checker）。verifier は書き込みツールを持たないので、構造的に「検証者が勝手に直して合格にする」事故が起きない。

### エスカレーションの梯子

triage(haiku) → executor-sonnet → executor-opus → Fable → **ユーザー**

- 下位で確信が持てない・境界に触れる判断は、必ず一段上へ上げる
- ユーザーへのエスカレーションは「何が起きたか・何を試したか・何を決めてほしいか」を 1 メッセージに揃えて行う

## ワークフロー定義（workflows/*.md）

各ワークフローは frontmatter で宣言的に定義する。スキーマは `workflows/TEMPLATE.md` 参照。要点:

- `executor`: sonnet / opus のどちらに実行させるか（Fable が負荷と複雑さで上書き判断してよい）
- `verify`: 受け入れ基準のチェックリスト。**空のワークフローは実行禁止**
- `boundaries`: 触ってよいパス・禁止事項。executor への指示に必ず転記する
- `trigger`: manual / cron / file。cron の武装方法は後述

## 実行プロトコル（/autopilot）

起動は Skill `/autopilot <workflow名>`。手順の正本は `.claude/skills/autopilot/SKILL.md`。概要:

1. **Load**: ワークフロー定義を読み、boundaries と verify が揃っているか確認（無ければ中止）
2. **Dispatch**: executor サブエージェントに、タスク・境界・出力先を自己完結した指示として渡す
3. **Verify**: verifier サブエージェントに「成果物 + 受け入れ基準」を渡し PASS/FAIL 判定させる。機械的チェック（テスト、lint、リンク検査）が定義されていればそれも走らせる
4. **Retry**: FAIL なら verifier の指摘を添えて executor に 1 回だけ差し戻し。2 回目の FAIL はユーザーへエスカレーション（自動で無限リトライしない）
5. **Log & Report**: `workflows/logs/YYYY-MM-DD-<name>.md` に実行記録を残し、結果を報告

## トリガーの武装（スケジュール実行）

定義しただけのワークフローは手動起動のみ。無人化するには:

- **Claude Code on the web / Routines**: `create_trigger` で cron + 新規セッション起動。prompt には自己完結の指示を書く（例: `リポジトリ claude_code で /autopilot repo-sweep を実行して結果を commit・push する`）
- **ローカル CLI**: OS の cron から `claude -p "/autopilot repo-sweep" --permission-mode acceptEdits` を叩く
- **ファイルトリガー**: 現状は「フォルダに置いたら次のセッション冒頭で /autopilot ingest-to-vault と言う」運用。完全自動化するなら inotify + CLI

コスト注意: cron トリガーは寝ている間も課金される。**1 本を 1 週間安定運用してから次を武装する**（記事の教訓: 壊れやすい 5 本を持つ者は 5 本の子守りをする）。

## 安全境界（変更してはならない不変条件)

1. verifier に書き込みツールを与えない
2. verify が空のワークフローを実行しない
3. 外部公開系の操作（メール送信、PR 作成、Slack 投稿、決済系）は draft 止まり。**送信・公開はユーザーの明示承認が必要**
4. 削除系は候補のフラグ付けまで。実削除は commit 差分としてレビュー可能にする
5. push は各ワークフローの `boundaries` が明示的に許可した場合のみ

## 運用のはじめ方

1. 既に毎日/毎週やっている作業を 1 つ選ぶ（このリポジトリなら `repo-sweep` か `ingest-to-vault` が初手に向く）
2. 手動 `/autopilot` で数回走らせ、出力を「ほぼ無編集で使えた」状態にチューニングする
3. 安定したら cron を武装する
4. 1 週間安定してから 2 本目を作る
