# ループエンジニアリング(Loop Engineering)の設計

エージェントに毎回プロンプトを渡す代わりに、**プロンプトを渡す仕組みそのもの**を設計する。組み込みの `/loop` は「一定間隔で再実行するだけ・止める判断を持たない」素のループに過ぎない。これに規律を与え、飼い慣らすための思想と判断基準をまとめる。SKILL.md 側は手順だけを持ち、ここに書くのは「なぜそう作るか」と「何を守れば壊れないか」。

## 3 つのループ(時間スケール別)

Andrew Ng の整理では、開発は入れ子になった 3 つのループが同時に回っている。

| ループ | 主体 | 時間スケール | 出力 |
|---|---|---|---|
| Agentic coding loop | エージェント自身 | 秒〜分 | 動くバージョン |
| Developer feedback loop | 人 + エージェント | 数十分〜時間 | より明確な仕様 |
| External feedback loop | ユーザー + チーム | 時間〜週 | ビジョンを進化させる実データ |

内側のループの出力が、外側のループの入力になる。動くバージョンが仕様を明確にし、明確になった仕様が現実のフィードバックでビジョンを更新する。ループエンジニアリングが設計対象にするのは主に一番内側だが、内側だけを最適化して外側との接続を切ると、速く回るが正しい方向へ進まないループになる。

## 抽象度の梯子(prompt → context → harness → loop)

Addy Osmani の整理に沿うと、エージェント運用の抽象度は 4 段ある。

- **prompt engineering**: モデルに何を言うか。
- **context engineering**: ウィンドウに何を載せる・いつ要約する・いつクリアするか。
- **harness engineering**: 1 回の実行を武装する — どのツールを持たせるか、何を「完了」とみなすか。
- **loop engineering**: harness の上にスケジューリングを重ねる — どう自走させるか、何ラウンド重ねるか。

loop が harness に加える動詞は 3 つ: **タイマーで走る**・**ヘルパーを spawn する**・**自分に食わせる**(今日の出力が明日の入力になる)。このうち最後の「自己給餌」こそがループをループたらしめる。同じタスクを N 回繰り返すだけの自動化と、前回の結果を踏まえて次を決める自己給餌は別物 — 前者は harness の反復適用、後者だけが loop engineering の対象になる。

## 1 ターンの中の 5 つの動き(背骨)

ループの 1 ターンは、次の 5 つの動きに分解できる。どれか 1 つでも欠けると、ループは走らないか、走っても前に進まない。

1. **Discovery**: 今回何をやるか決める。
2. **Handoff**: タスクを配って隔離する。
3. **Verification**: "no" と言う。
4. **Persistence**: 会話の外 — ディスク — に状態を書く。
5. **Scheduling**: このターンを次のターンに食わせる。

Verification が「no と言う動き」、Scheduling が「今回を次回に食わせる動き = ループにする動き」であることは明記しておく。Scheduling を欠くと 1 回限りのタスク実行で終わり、Verification を欠くと止めどなく壊れたものを積み続ける。

## 5 つの病(アンチパターン)と処方

| 病 | 症状 | 処方 |
|---|---|---|
| Blind Loop | 実行は自動化したが「選ぶ(Judge)」を人が毎朝渡している。ループが決して驚かせてくれない | Judge を skill の中に入れ、今日やる仕事をループ自身に選ばせる |
| Tangled Loop | 複数エージェントが同じディレクトリ/ファイルを編集し、マージが考古学化する | finding ごとに専用 git worktree を割り当て、作業ディレクトリを共有しない |
| Nodding Loop(最も高くつく病) | コードを書いた同じエージェントが「良さそう」と自己承認する | 別プロンプト・できれば別モデルの評価者を立て、デフォルト懐疑(ASSUME BROKEN)、意図でなく挙動で判定し、第三者の停止条件を持つ |
| Amnesiac Loop | 成果が flush される context にしか無く、毎日ゼロから再トリアージする | 状態をディスク(markdown/DB/board)に書く |
| Manual Loop | 5 つの動きは美しく作ったが cron が無い — 一度走らせて忘れたスクリプト | 自分が覚えていることに依存しないトリガーを掛ける |

**Nodding Loop の補足**: 自分の宿題を自分に採点させると必ず自分を褒める。これは構造的な欠陥であって、モデルが馬鹿だからではない。GAN の生成器と検証器が別モデルであるように、銀行で「送金する人と承認する人は別人」であるように、生成と検証は役割として分離しないと機能しない。

**Amnesiac Loop の補足**: CONTEXT(今ターンだけ見えるウィンドウ、毎回消える)と MEMORY(ターン/日をまたいで生きる、ディスク上の状態)を区別する。ループが賢くなるのは MEMORY を持つ場合だけで、CONTEXT だけに頼るループは毎朝振り出しに戻る。

**Manual Loop の補足**: 「ローカルタイマーは自分が寝てる間も走ってくれる」は自己欺瞞になりやすい。実際に起きているのは「自分がまだセッションに居る間に数ターン多く回る」だけで、離席後は止まる。この区別がスケジューラ選択(後述)の判断軸になる。

## 検証の扉(Verification を最重視する)

Anthropic の Prithvi Rajasekaran の言葉を借りると、「独立した評価者を懐疑的にチューニングする方が、生成器に自作を批判させるよりはるかに扱いやすい」。評価者に持たせる要件は次の 5 つ。

- **ROLE**: 敵対的レビュアーとして振る舞う。
- **ASSUME**: 証明されるまで壊れているとみなす(ASSUME BROKEN)。
- **CHECK**: 実行順を守る — 動くか確認する → テストを実行し実出力を貼る → 著者が飛ばしたエッジケースを探す → チケットと挙動が一致するか確認する。
- **USE**: 挙動そのものを検証する道具を使う。frontend なら Playwright、API なら curl/httpie。
- **VERDICT**: 全チェック通過時のみ PASS、さもなくば REJECT とし、各理由を列挙する。

**酸のテスト**: 直近 5 ターン以上にわたって評価者が一度も no を言っていないループは、どんな現実のワークロードに対しても統計的にありえない。評価者が実質働いていない証拠として扱う。

**理由なき REJECT は REJECT ではない**: 生成器は何を直せばいいか分からないまま同じ失敗を繰り返す。REJECT には必ず具体的な理由を添える。

## 人間の扉とキャップ(安全)

ループを走らせる前に、3 層のキャップを設定する: **per-run(タイムアウト)・daily budget・max retries**。トークンキャップは節約策ではなく**サーキットブレーカー**であり、青天井のリスクを有界にするための装置。Uber が「1 人 1 ツール月 $1,500」に制限した例が典型。

人間の扉は次のように置く。

- PR は自動マージしない。
- 不確実なものは `./inbox/` へ落とす。
- 1 日 1 本サンプル PR を読み、「何がなぜ変わったか」を自分の言葉で説明できるか自問する。説明できない瞬間が、自分の地図がループに遅れ始めた合図。

扉があるのは「人が必ず通るから」ではなく、「扉が在ること自体が"通れる立場"を保つから」。Stripe は週 1000 以上の PR をループで回すが、人が全部レビューする — これは人が工程から抜けたのではなく、**机を変えた**(コードを書く机からレビューする机へ)ことを意味する。Stripe が採用したのは最大モデルではなく、小さいモデル + 厳格な決定論的ゲートの組み合わせであり、「厳しい検証ゲートは生モデル力に勝つ」ことを示している。

## スケジューラの選択

| スケジューラ | 最小間隔 | マシン電源 | セッション | ローカルファイル |
|---|---|---|---|---|
| Cloud(GH Actions) | 1 時間 | 不要 | 不要 | 見えない |
| Desktop scheduled | 1 分 | 必要 | 不要 | 見える |
| `/loop`(Claude Code 内) | 1 分 | 必要 | 必要 | 見える |

判断基準は「この仕事はラップトップを離れられるか」の一点。ローカルファイルを毎分ポーリングする仕事は `/loop`、深夜 3 時の GitHub 巡回は cloud に置く。Manual Loop の節で触れた「ローカルタイマーは寝てる間も走る」という誤解は、この表で言えば `/loop` や desktop scheduled をセッションが無いのに使おうとするところで起きる。

## 6 つの能力(ベンダー非依存)

問うべきは「どのベンダーか」ではなく「6 つの能力すべてが載っているか」。

- scheduling
- run-to-condition
- parallel isolation
- sub-agents
- external connect
- explicit skill

Claude Code での対応は: scheduling = `/loop`・worker、run-to-condition = `/goal`、parallel isolation = `--worktree`、sub-agents = `.claude/agents/`、external connect = MCP + plugins、explicit skill = SKILL.md。

`/loop`(一定間隔で再実行するだけ、停止判断なし = 危険)と `/goal`(新鮮なモデルが条件を true と判定するまで走る)は別物であることを強調しておく。`/loop` に Verification を組み込まずに使うと、そのまま Blind Loop か Nodding Loop に落ちる。

## 静かに積む 4 つの負債

ループが不健全なまま回り続けると、次の 4 つの負債が互いに餌を与え合いながら積み上がる。

- **VERIFICATION DEBT**: 未リジェクトの出力が積み上がる。
- **COMPREHENSION ROT**: コードベースは育つが、自分の頭の中の地図は育たない。
- **COGNITIVE SURRENDER**: もう精査する気力が残っていない。
- **TOKEN BLOWOUT**: バグが一晩中回り続け、翌朝請求として気づく。

VERIFICATION DEBT が COMPREHENSION ROT を招き、地図を失うと COGNITIVE SURRENDER に陥り、精査を諦めた先で TOKEN BLOWOUT が起きる — という連鎖として見る。

ループは忠実な増幅器である。理解を持ち込めば理解を、怠惰を持ち込めば怠惰を増幅する。何を増幅したいかを、作る前に決めておく。Addy Osmani の言葉を借りれば、作れ、ただし「go を押す人」としてではなく、「エンジニアであり続けるつもりの人」として作れ。
