# Obsidian vault(second brain)の設計

エージェント(Claude Code)が読み書きする知識基盤を Obsidian vault として運用するための設計書。発想は 2 つ:

- Karpathy の llm-wiki: **知識ベースをコードベースのように扱う。Obsidian はエディタ、モデルはプログラマ、wiki がコード。**
- 3 層知識スタック: **Obsidian = 記憶の地層、Claude Code = 操作員(読む・渡す・書き戻す)、モデル = 推論エンジン。** 3 層が分断されると「ノートは溜まるが AI に渡らない」記憶の断絶が起きる。書いたノートが AI に渡り、処理結果が vault に戻り、次の文脈になるループを設計する。

vault はただの Markdown フォルダなので、モデルを乗り換えても生き残る(モデル非依存)。

## 構造

```
vault/
├── raw/          # 人間が書く層。無加工の ground truth。エージェントは読むだけ
│   ├── inbox/               # 生のアイデア・メモ・クリップ。整理を気にせず書き込む
│   ├── daily/               # 日次ログ(作業・決定・気づき)。低摩擦で書き続ける
│   ├── reading/             # 読んだ記事・本のハイライト/引用
│   └── ClaudeChat Memory/   # claude.ai 会話エクスポート(scripts/claude_export_to_obsidian.py が上書き管理)
├── entities/     # AIが整理する層: 具体物 1 つにつき 1 ページ(クライアント、競合、ツール、人)
├── concepts/     # AIが整理する層: 概念 1 つにつき 1 ページ(戦略、パターン、教訓)
├── reviews/      # AIが書く層: 日次/週次サマリー、週次 synthesis の着地先(日付付き)
└── INDEX.md      # 玄関。全ページを 1 行説明付きで列挙 + タグの固定スキーマ定義
```

**書き込み境界(最重要)**: raw/ は人間(と取込スクリプト)が書き、エージェントは読むだけ。entities/ concepts/ reviews/ はエージェントが書き、人間はレビューする。境界が曖昧だとエージェントは「改善」ではなく「どこに何を書くべきかの解釈」にコストを費やす。境界が明確なら即座に作業へ入れる。

- **raw/ をエージェントが書き換えない理由**: 同じノートを読んで書き直すサイクルを繰り返すと詳細が磨耗し誤りが複利で増える。compiled 側が壊れても raw から再コンパイルできるのが保険になる。
- entities/ と concepts/ が「コンパイル済み」の知識。エージェントの仕事はコンパイル: raw/ の新素材を読み、ページを更新し、`[[wikilink]]` で繋ぐ。
- リンクはグラフの辺。検索型の知識ベースは成長するほどノイズが増えるが、リンク型 wiki は成長するほど強くなる。エージェントは全走査せず**リンクを辿って**答えに着く。「書いたら保存」ではなく「書いたらリンクで繋げる」。
- INDEX.md があるから、全ファイルを開かずに何が存在するかを知れる。

## 書き込みルール

1. 1 ファイル 1 教訓。冒頭に 1 行要約を置く。
2. 重複ページを作らず、既存ページを更新する。
3. 誤りと判明したノートは削除する。
4. raw と compiled を混ぜない。raw/ は書き換えない。
5. **仮リンク(forward reference)は歓迎**: まだ存在しないページへの `[[リンク]]` を書いてよい(Obsidian ではグレー表示される)。ただし放置しない — 週次 lint で「ページを作る / まだ待つ / 消す」を精査する。
6. **タグは固定スキーマ**: 使えるタグは INDEX.md に定義した一覧だけ。エージェントに自由発明させない(スキーマ外のタグを付けたくなったら、まずスキーマ側を更新する)。

加えて出典の規律: compiled ページの主張には raw/ 内の元ファイルへのリンクを付ける。**出典リンクの無いページはフラグ対象**(信用せず、dream で検証・除去の候補にする)。

## 読み取りルール(コスト管理)

- CLAUDE.md は **vault を指すだけ**にする(200 行未満)。vault の内容を貼り込まない — 毎セッション自動ロードされる固定税になる。
- 日常の読み方は pay-per-read: INDEX.md を見る → リンクを辿る → grep で絞る → 必要なページだけ開く。**フォルダ全読みは日常セッションでは禁じ手。**
- 大きい問いは subagent に読ませる: 別コンテキストで 50 ページ読ませ、結論の 1 段落だけを受け取る。メインの context window には決定を置き、図書館は置かない。
- **例外は全体横断パス(lint / synthesis)**: タグ付けやリンク判断の精度は「タグ体系・リンク構造の全景が一度に文脈へ入っているか」で決まるため、横断パスでは subagent に vault を広く読ませてよい。日常の pay-per-read と横断パスの一括読みを混同しない。

## 維持ループ(放置した vault は 3 週間で死ぬ)

| 頻度 | 作業 | 書き込み先 | モデル tier |
|---|---|---|---|
| セッション毎 | 決定・失敗・気づきを日付付きで記録(hook / 記憶ルールで自動化) | raw/daily/ | セッションのモデル |
| 定期(日次目安) | compile: raw/(inbox・reading・会話ログ)の新着を entities/concepts へ反映。前日の daily から日次サマリー | entities/ concepts/ reviews/ | 安価(Sonnet/Haiku) |
| 週次 | lint: 矛盾・重複・リンク切れ・孤立ノート・仮リンク精査 = **memory-dream Skill を実行** | entities/ concepts/ INDEX.md | 安価〜中位 |
| 週次 | synthesis: vault 全体を横断し「今週何が変わったか・何がドリフトしているか」を 1 ページ書く | reviews/ | 上位(Opus 級) |

ルーチン作業(ノート更新)を上位モデルに回さない。上位モデルが席代を稼ぐのは synthesis だけ。このループが回っている限り、メンテナンスは「維持するもの」ではなく「育つもの」になる — 積み上がった処理結果が次の作業の文脈になる複利設計。

## 最小実践パス(始め方)

「完璧な vault を作ってから」は始めない理由になる。1 フォルダ・1 タスク・1 ループから:

1. Claude Code に vault のパスを渡す(作業ディレクトリに指定するだけ)
2. 対象を 1 フォルダに絞る: まず raw/inbox/ だけ
3. 1 タスクを実行: 「raw/inbox/ の新着を読んで entities/concepts に整理して」
4. **Obsidian 側で出力を確認する**: どこに書かれたか、リンクとタグは適切か

ループが安定したら daily サマリー → reading の変換 → 週次 lint の順に拡張する。

## バックフィル(初期投入)

1. 手持ちを全部 raw/ に投げ込む: 会話エクスポート(スクリプトで自動)、ブックマーク、メモアプリの export、過去リサーチ。
2. エージェントに compile を指示する。ただし 2 つの規律で正直に保つ:
   - 変更は必ず **diff で提示**させる(「更新した」という主張ではなく before/after)。
   - raw/ への出典リンクの無いページはフラグする。
3. 一括で終わらせようとしない。会話履歴が数百件あるなら dream のたびに少しずつ消化するインクリメンタル方式でよい。

## プロジェクトへの接続

各プロジェクトの CLAUDE.md に 3 行入れるだけで、全プロジェクトが vault を参照するようになる:

```markdown
## knowledge
- 開始前に ~/vault/entities/ と ~/vault/concepts/ の関連ページを読む
- 事業・クライアント・読者に関する主張は vault のページを根拠にする
```

## 同期の注意(vault が死ぬ場所)

**同期系は 1 本にする。** エージェントがファイルを書いている最中に iCloud / Obsidian Sync が同期すると、conflicted copy とフォルダ破損が起きる。チェックポイント層は git — 明示的に commit した時だけ版が確定する構成が生き残る。

## 採用しなかったもの(判断メモ)

- `/goal` によるバックフィル自動化: 元記事が主張する Claude Code 機能として確認できない。バックフィルは通常の指示(+ 上記の diff / 出典規律)で足りる。
- 5 フォルダ構成(Inbox/Daily/Reading/Projects/Reviews)の並列採用: 「人間が書く層 / AI が整理する層」という書き込み境界の思想だけ取り込み、フォルダは raw/ のサブフォルダ + reviews/ に統合した。capture 系 3 つを raw/ 配下に集めることで「raw 不可侵」の原則が 1 つのルールで済む。Projects/ は entities/concepts と役割が重複するため不採用。
- Hermes / MiniMax M3 等の特定ツール前提: Claude Code + subagent で代替。設計原則(3 層・横断パスに広い文脈)だけ採用。
- 外部リサーチスタック(ScrapeCreators / X MCP / Firecrawl / Perplexity 等): 有償・ニッチ依存。導入する場合も骨格だけ持ち込む: 問いをサブ問いに分割 → 並列 fan-out → 主張・出典 URL・日付の「受領書」形式 → **リサーチしていない別コンテキストの懐疑エージェントが反証を試み、生存した主張だけ** vault へ、日付+出典+失効日付きで着地。
- 記事中の数値(精度 70→90%、タグ精度 60→90%、8〜9 回のツール呼び出しでドリフト、3 倍改善等): 一次出典が薄く検証不能。「横断パスには広い文脈を与えるほど精度が上がる」「構造化されていない vault は射程を増やしても改善しない」という方向性だけ採用し、数値は根拠にしない。
