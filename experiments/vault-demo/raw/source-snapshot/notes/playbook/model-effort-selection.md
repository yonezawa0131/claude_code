# モデルと effort の使い分け

出典: Anthropic の解説記事(2026-07 読了)。一言でいえば **モデル = 何を知っているか(能力)、effort = どれだけ働くか(徹底度)**。結果に不満なとき、設定より先にコンテキストを疑い、それでもダメなら「知らなかったのか、頑張らなかったのか」で触るツマミを決める。

## 仕組み: モデル設定が実際にやること

- Enter を押すと、プロンプト + システムプロンプト + ツール定義 + CLAUDE.md + 会話履歴 + コンテキスト内ファイルが 1 つの API リクエストに束ねられ、サーバー側で最初にトークン化される(テキストを固定語彙の断片に分割し、各断片を整数に写像。以後プロンプトは整数の配列)。
- モデルの仕事は「次の 1 トークン」を予測すること。語彙全体に確率を計算し、上位から選ぶ。応答は一度に生成されず、1 トークン予測 → 配列に追記 → 全体を再計算、の繰り返し(200 トークンの応答 = 200 回の重み通過)。待ち時間と出力コストの大半はこのループ。
- 入力トークンを確率に変える実体が **重み(パラメータ)** — 巨大な行列に組織された数十億の数値で、モデルが「知っている」ことは全部ここに住む。重みは訓練時に固定され、推論(inference)時は読み取り専用。プロンプトも CLAUDE.md もコンテキストも重みを変えない。
  - コンテキストにできるのは予測の**操縦(steering)**だけ。実コードを見せるのは操縦で、非常によく効く。だが訓練後に登場したライブラリは重みに無い — docs をコンテキストに入れれば使えるが、それは steering であって teaching ではない(そのリクエスト限りで、モデルには何も残らない)。
  - 幻覚(存在しない API を自信満々に呼ぶ)は「検索の失敗」ではなく、訓練パターンから尤もらしく見えるトークン列が生成された結果。
- つまり**モデル設定を変える = どの凍結された重み一式で処理するかを差し替える**こと。出力トークン単価もここで決まる。ただし「何トークン生成されるか」はモデル設定では決まらない — 同じプロンプトでも Claude がどれだけ働くかで大きく変わる。それを決めるのが effort。

## 仕組み: effort が実際にやること

- 作業中に生成されるトークンは 3 種 — **thinking**(行動の前後に流れる推論)、**ツール呼び出し**(Read/Edit 等を指名する構造化ブロック)、**ユーザー向けテキスト**(計画・進捗・要約)。全部同じループから生成される同料金の出力トークンで、thinking もそのターンの残りでは入力(コンテキスト)になる。コードを書く頃には、先の推論は読んだファイルと同じ扱いで入力に入っている。
- effort はプロンプトと並んでリクエストの一部としてモデルに送られる入力。モデルは各 effort 水準での振る舞いを訓練済みで、その学習された挙動は凍結された重みに焼き込まれている。**タスクを「完了」と見なすまでに要求される徹底度・確信度を設定し、毎ターン秤にかけられる。高い確信に達するには多くのトークンが要る。**
- effort が上げるのは thinking 時間だけではない: **読むファイル数、検証の量(テスト実行・二重チェック)、確認を挟まずに多段タスクを進む距離**。低 effort では、自力でトークンを使って調べるよりユーザーに文脈を聞く方へ倒れる。
- 高 effort は計画から始まることが多く、effort は計画の深さと幅に影響する。ただし計画は凍結されない — 仮説 1 で原因が見つかれば「残りの確認は不要」と明言してスキップする(Claude Code でタスクリストが途中改訂されるのがこれ)。高 effort は見つけた答えの検証やスキップ可能だった仮説の追跡をやりやすくするが、**単純タスクで使用量を人工的に膨らませはしない**(overthinking は訓練時に劣化として監視される)。
- effort はトークン消費を「形作る」が「制限しない」。唯一のハードキャップは max_tokens で、応答を途中で切断する鈍器(主に API 開発者向け)。タスク予算や「簡潔に」等のプロンプト指示の方が有用 — モデルが従うよう訓練された誘導であり、上限に近づくと畳みに行く。

## 使い分けの判断手順

1. **設定を触る前にコンテキストを疑う**: プロンプトは曖昧でないか、正しいツール・Skill に繋がっているか、自分の作業を検証する手段を与えているか。effort を上げたくなるタスクの多くは上流(コンテキスト・CLAUDE.md・タスクの切り方)で直る。
2. 明確なコンテキストを与えても間違うなら: **知らなかったのか(→ モデルの問題)、頑張らなかったのか(→ effort の問題)**。
   - **モデルを上げる**: 本質的に難しい問題 — 微妙なバグ、馴染みの薄いドメイン、アーキテクチャ判断。いくらコンテキストを与えても自信満々に間違い続けるとき。曖昧さの処理も大きいモデルが得意(小さいモデルには実行を方向づける具体的指示が効く)。
   - **effort を上げる**: 試行の不足 — ファイルを読み飛ばした、テストを回さなかった、二重チェックしなかった。特にデフォルト未満に下げていた場合に該当しやすい。
3. effort は**タスク毎の判断ではなく一般的な好みとして**設定する。基本はデフォルト(モデルが「大半の人がそのタスクに使いたい量」にトークン消費をスケールする水準)。ドメインや作業の種類として速度/徹底への強い好みがあるときだけ意図的に上書きする。
4. **ルーチンが続いたら小さいモデルへ落とす**: 正確に記述できる編集、機械的な変更、コンテキスト内コードへの質問に大きいモデルの能力は不要。品質を落とさず速度が上がりコストが下がる。

## コストの直感

- **ルーチン作業**(同 effort): どちらのモデルでも正解する。大きいモデルは検証を余分にやり単価も高い → 小さいモデルに落とすのが品質コストゼロの純益。
- **難しい多段作業**: 等式が反転する。小さいモデルは能力の限界に向かって反復を燃やし、大きいモデルは少ない手数で同じ品質に届く。単価は高くても**タスク単位の総額は大きいモデルの方が安くなり得る**。さらに重要な点として、小さいモデルではどの effort でも届かないタスクがある(長い多段作業で最も差が開くのが Fable で、Opus/Sonnet がどの effort でも到達できないジョブを完了する)。
- effort はこの品質曲線上を「どこまで進んでよいか」を決めるだけで、タスクを終えるのにそこまで必ず使うという意味ではない。

## 人格メタファー(覚え方)

- **Sonnet = 優秀なジェネラリスト**: 高 effort なら「午後いっぱい使える人」— 全部読み、動かし、二重チェックし、あなたの具体的なコードを一番よく理解した状態になる。
- **Opus = 経験豊富なエキスパート**: 低 effort でも「似た問題を大量に解いてきた人の 5 分」— コードベースのどこにも無い知識(既知のパターン、チェックすべき落とし穴)を持ち込む。ただし 5 分なので全ファイルの丁寧な通読はしない。
- **Fable = 皆が詰まったときに呼ぶスペシャリスト**: 低 effort でも他の誰も見抜けない点を見つける。その認識力に最も高い対価を払っているので、本当に必要なタスクに温存する。

どれが普遍的に「良い」わけではない。**モデル ≒ どれだけ有能か、effort ≒ どれだけ徹底的か**。実タスクの多くは両方をいくらかずつ必要とする。

## このリポジトリでの適用

- vault 維持ループのモデル tier 分け(`obsidian-vault.md` の表: ルーチンの compile = 安価モデル、意味の統合 synthesis = 上位モデル)はこの原則の適用例。「ルーチンを上位モデルに回さない」「上位モデルが席代を稼ぐ仕事に温存する」はコストの直感の節と同じ主張。
- チーム運用(Fable = 頭脳: 設計・採用判断・レビュー、Sonnet = 手足: 定型の展開・検証)も同じ軸の適用。
- 「うまくいかない → まず Skill / playbook / プロンプトを直す」を第一手にする。effort・モデル変更は第二手。

## 採用しなかったもの(判断メモ)

- 記事中の具体数値(高 effort パスは約 7 倍のトークン、Opus 4.8 のデフォルト effort は 4.7 と同トークンでより良い結果、等): グラフは "illustrative purposes only" と明記されテスト詳細も非公開。方向性(effort ↑ = トークン ↑、新世代はデフォルト効率が改善)だけ採用し、数値は根拠にしない。
- effort のタスク毎切り替え運用: 記事自身が「一般的な好みとして扱え」と言っており、タスク単位の微調整はしない。
- max_tokens による出力制御: API 開発者向けの鈍器。Claude Code の運用ではプロンプトでの誘導(簡潔に・予算指示)を使う。
- トークナイザーの具体例(`const` → 1978 等): 記事内でも "IDs shown are illustrative" — 仕組みの説明としてだけ保持し、実際の ID とは扱わない。
